# x-out: перемешивание групп в подписке

Локальная ветка `out/x-out` основана на upstream `8.0.0`. Расширение находится в
`backend/src/modules/subscription/x-out.ts`; `subscription.service.ts` вызывает его
непосредственно перед отправкой готовой подписки. Основной backend Remnawave менять
не требуется.

## Настройка

```yaml
proxy-groups:
  - name: 🇷🇺 Без рекламы
    type: fallback
    x-out:
      randomize: true
      mode: per-refresh
    remnawave:
      include-proxies: false
    proxies:
      - ♻️ 🇷🇺 Hades
      - ♻️ __[yt]Nlades
```

При каждом запросе подписки используется независимая перестановка Фишера — Йетса
с `crypto.randomInt`. Список может случайно остаться в прежнем порядке. Обработчик
меняет только порядок `proxies` в отмеченной группе: содержимое вложенных групп,
провайдеры, DNS, правила и учётные данные сохраняются. Поле `x-out` удаляется из
групп перед отправкой. Подписки без таких полей проходят побайтно без изменений.

Реализован только `per-refresh`; это также значение по умолчанию при отсутствии
`mode`. `randomize: false` удаляет маркер, сохраняя порядок. Неизвестный режим или
некорректные параметры сохраняют порядок и дают предупреждение без содержимого
подписки. Некорректный YAML и ответы больше 8 МиБ возвращаются без обработки.
Ограничено раскрытие YAML-алиасов.

В изменённом ответе удаляются устаревшие заголовки длины, кодирования и валидаторы;
добавляется `Cache-Control: private, no-store`. Прокси перед сервисом также должен
уважать этот заголовок и не кешировать подписки. При обходе subscription-page и
прямом запросе к панели расширение не применяется.

## Проверка и сборка

```sh
cd backend
npm ci
npm run typecheck
npm test
NODE_ENV=production npm run build
npm run trace
cd ..
docker build -f Dockerfile.x-out -t out/subscription-page:8.0.0-x-out.1 .
node scripts/smoke-x-out.cjs out/subscription-page:8.0.0-x-out.1
```

`Dockerfile.x-out` берёт frontend и runtime из официального образа, закреплённого
по digest, а сервер собирает из текущей ветки. Проверки типов и тесты обязательны
при сборке. UI не меняется; существующие mounts с оформлением страницы сохраняются.

## Обновления upstream

Форк: https://github.com/ckeiituk/subscription-page. Основная ветка — `out/x-out`,
`origin` указывает на форк, `upstream` — на `remnawave/subscription-page`.

Workflow `Update Remnawave upstream` проверяет стабильные Git-теги
каждый час на 23-й минуте; также доступен ручной запуск в Actions.
GitHub может задерживать запуск по расписанию. У Remnawave нет GitHub Releases
для subscriptions: версия определяется по наибольшему тегу `X.Y.Z` или `vX.Y.Z`,
без prerelease. Появление нового тега без готового Docker-образа даёт ошибку
проверки; следующий запуск повторит попытку.

Для новой версии workflow создаёт отдельную ветку `out/upstream-VERSION`, вливает
тег, обновляет версию и digest образа в `Dockerfile.x-out` и открывает PR. Существующие
PR и ручные исправления не перезаписываются. Закрытый PR считается отклонённым:
бот не открывает его заново. Если слияние конфликтует, оно отменяется, а draft PR
содержит только `.github/x-out-upstream-conflict.md` со списком файлов и инструкцией.
Проверки такого PR намеренно завершаются ошибкой, пока отчёт не удалён после
ручного разрешения конфликтов.

После создания PR явно запускается `Check x-out` на его ветке: тесты обновлятора,
TypeScript, тесты backend, сборка и проверка работающего контейнера. После проверок основной ветки GitHub Actions собирает и проверяет итоговый образ,
публикует архив и SHA-256 в публичном Release `x-out-COMMIT`. Registry не требуется. После успешных проверок PR бота автоматически сливается; сервер устанавливает
образ проверенного коммита по схеме ниже.

Для запуска автоматизации в форке включены Actions и разрешение «Allow GitHub
Actions to create and approve pull requests». Workflow использует встроенный
`GITHUB_TOKEN`, отдельный PAT не нужен. Обновлятору даны права на запись веток,
создание PR и запуск проверок; workflow проверок имеет только `contents: read`.
Унаследованные workflow публикации ограничены исходным репозиторием Remnawave.
Расписание работает только из default branch, поэтому `out/x-out` должна оставаться
основной веткой. Чтобы GitHub не отключил расписание после 60 дней без активности, обновлятор
при отсутствии коммитов в течение 30 дней создаёт небольшой heartbeat-коммит
и запускает его проверку.

Ограничения токена и расписаний описаны в [GitHub Docs](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows).

Для ручного обновления: создать ветку от `out/x-out`, выполнить
`git fetch upstream --tags` и `git merge VERSION`, обновить digest и label в
`Dockerfile.x-out`, затем выполнить проверки из раздела выше. При новых требованиях
upstream отдельно обновить Node builder и тестовые данные runtime-проверки.

Обновление официального `latest` не обновляет нашу сборку. В compose должен быть
указан собственный точный тег, а не `remnawave/subscription-page:latest`. Для локально
собранного образа используйте `pull_policy: never`; для собственного registry — его
адрес и опубликованный неизменяемый тег. Храните предыдущий образ для отката.

Для отката вернуть предыдущий тег и пересоздать только сервис subscription-page.
При откате на официальный образ сначала убрать `x-out` из шаблонов или учитывать,
что порядок перестанет перемешиваться.


## Автоматическое слияние и установка на sber

Ручной approve для обычного обновления не нужен. Обновлятор запускается каждый час
и после завершения `Check x-out` для веток `out/upstream-*`. Он принимает только
готовые PR `github-actions[bot]` внутри этого форка, в ветку `out/x-out`, с ожидаемым
именем ветки релиза. Сначала он обновляет устаревшую базу PR. Затем требует успешный
`push`/`workflow_dispatch` запуск `Check x-out` именно для текущего head SHA. Более
новый проваленный или незавершённый запуск не заменяется старым успешным.
Слияние атомарно ограничено проверенным head SHA. После него отдельно запускается
CI итогового коммита основной ветки: сервер не устанавливает непроверенный merge.

Изменения `.github`, `scripts`, `deploy`, тестов backend, настроек TypeScript, обработчика
`x-out.ts` или Dockerfile расширения (кроме версии/digest upstream) требуют ручного
разбора. Конфликтный draft PR, сторонний PR и проваленные проверки не сливаются.
Проваленный CI не перезапускается автоматически до получения случайного зелёного.

На `sber` служба `remnawave-subscription-update.service` запускается таймером каждые
15 минут и после загрузки сервера. Она читает публичный GitHub API без токенов и
проверяет последний запуск CI для точного коммита `out/x-out`, включая публикацию
образа в GitHub Release. Ключи сервера и
production-секреты в GitHub не передаются.

До замены рабочего контейнера служба скачивает уже проверенный образ с полным SHA
в теге, проверяет SHA-256 архива, автора и коммит Release, revision label образа,
загружает его в Docker и запускает изолированный тест: 24 выдачи подписки, перемешивание пар, неизменность вложенных
групп, gzip, заголовки и обычная подписка без маркера. Рабочий контейнер всё это
время продолжает работать. Для скачивания и загрузки нужно не менее 3 GiB свободного диска.
Сборка на production не выполняется: на сервере с 4 GB RAM она создаёт давление
на память, поэтому все npm/TypeScript/Docker build шаги выполняются в GitHub Actions.
Обновлятор сохраняет рабочий и предыдущий образы, удаляя только более старые
собственные теги `out/subscription-page:git-*`. Общие кеши, чужие образы и volumes Docker не очищаются.

Перед переключением сохраняются исходный compose и точный image ID предыдущего
контейнера. Меняется только `image` сервиса подписок: `.env`, mounts, оформление
и остальные контейнеры сохраняются. После переключения проверяются health и выдача
Mihomo-подписки существующего аккаунта checker без вывода URL и учётных данных.
Если рабочая выдача использовала `x-out`, новая должна продолжать его применять.
При неудаче восстанавливаются compose и предыдущий image ID, затем повторяется
проверка выдачи. Перезапуск даёт короткий перерыв в получении подписок; уже
работающие VPN-подключения не затрагиваются.

Неудачный SHA записывается в state и повторно сам не устанавливается. При следующем
новом проверенном коммите обновления продолжаются. При конфликтующей ручной правке
compose откат останавливается, сохраняя правку оператора. Не удаляйте предыдущий
образ, пока он нужен для отката. Сам установленный helper обновляется явным
повторным запуском installer, а не из загруженной непроверенной ветки.

### Первичная установка

Выполнить на сервере после успешного CI основной ветки:

```sh
git clone --branch out/x-out https://github.com/ckeiituk/subscription-page.git /opt/remnawave/subscription-source
cd /opt/remnawave/subscription-source
sh deploy/install-systemd.sh
systemctl start remnawave-subscription-update.service
```

Installer устанавливает root-owned helper в `/usr/local/libexec`, две systemd units
и включает таймер. Используется существующий compose
`/opt/remnawave/subscription/docker-compose.yml`; контейнер `checker` служит источником
контрольного URL. Node.js на хосте не нужен: Python-лаунчер запускает Node внутри
проверяемого образа.

### Диагностика и остановка

```sh
systemctl status remnawave-subscription-update.timer
journalctl -u remnawave-subscription-update.service -n 50 --no-pager
cat /var/lib/remnawave-subscription-update/state.json
systemctl stop remnawave-subscription-update.timer
```

Вывод сборки доступен в GitHub Actions; резервные копии
compose на сервере лежат в `rollback-*` рядом со state. После устранения причины сбоя однократный повтор:

```sh
python3 -B /usr/local/libexec/remnawave-subscription-update.py --retry
```

Если GitHub API недоступен, CI ещё не завершён или проверка не прошла, рабочий образ
не меняется. Обычный `docker compose pull` по-прежнему пропускает локальный образ
из-за `pull_policy: never`; это не отключает таймер обновлений.

Поведение `GITHUB_TOKEN` и явного dispatch: [GitHub Actions](https://docs.github.com/en/actions/how-tos/write-workflows/choose-when-workflows-run/trigger-a-workflow).
Ожидание health: [Docker Compose up](https://docs.docker.com/reference/cli/docker/compose/up/).
